# ShadowWork Bench 结果 · spec 0.4

> **这一版只做了一件事：把对照组换成一个不是我们写的实现。**
>
> spec 0.3 的三个对照臂——尾部截断、自制 summary、自写词法 RAG——全部出自我们自己手里。
> 跟自己的手艺比出来的「更有效」，是「自证」在 benchmark 层的最后一处藏身点：
> 每个部件都真实、每个数字都可复算，但对照组的天花板是我们自己能写多好。
> 所以 0.4 接进 **mem0 2.0.17**（引用最多的开源 memory 层），同语料、同预算、同模型。

运行：`2026-08-09T03:43:25Z` · 模型 `deepseek-v4-flash` @ `api.deepseek.com/v1` · temperature 0
语料：磁盘上 10 份真实学历 + 2 份真实 Claude Code 会话记录（渲染 261,864 字符）
预算基准：本境 bundle 实际 9,405 字符，除 `transcript-10x` 外各臂同预算
题量：76 题/臂 × 7 臂 = 532 次调用，**0 个调用错误、0 条残留截断**

## 2. 结论（第 ① 条在发布前被我们自己的复核改写了，见 §2.5）

### ① 主结论在真实第三方对照面前站住了——但**机制不是我一开始写的那个**

表面数字：事实召回 **97.5% [87.1, 99.6]** vs 同预算最强对照 **mem0 55.0% [39.8, 69.3]**，
Wilson 区间不重叠，2origin 的下界（87.1）高于任何对照臂的上界（最高 rag 的 73.7）。

**这句话算术没错，但把它读成「同样的信息，结构化表示更好用」是错的。**
`bench/corpus-availability.mjs` 复核发现：20 条真事实里有 **10 条的答案压根不在对照语料里**
（学历是活文件，被后来的会话继续写过；而对照语料是钉死的两份会话记录）。
拆开看，差距由**两件不同的事**组成，必须分开讲：

| | 2origin | rag（自写） | mem0（第三方） | transcript | none |
|---|---|---|---|---|---|
| 真事实 TPR·**答案在语料里**(n=10) | 90.0% [59.6,98.2] | **90.0% [59.6,98.2]** | 70.0% [39.7,89.2] | 0.0% | 10.0% |
| 真事实 TPR·答案不在语料里(n=10) | 100.0% | 40.0% | 30.0% | 0.0% | 20.0% |
| **假事实 TNR**(n=20) | **100.0% [83.9,100.0]** | 55.0% [34.2,74.2] | 60.0% [38.7,78.1] | 80.0% | 75.0% |

**答案在语料里时，自写词法 RAG 与 2origin 打平（90% vs 90%，区间完全重合）。**
在「找得到吗」这件事上，我们没有证据说结构化状态更强。

### ①′ 真正分得开的是**拒绝**，不是召回

唯一区间不重叠、且不受语料可得性干扰的一列是 TNR：
**2origin 100% [83.9, 100.0] vs 最强对照 mem0 60% [38.7, 78.1] / rag 55% [34.2, 74.2]。**

题目问的是「这句话是不是**当前这个任务**已经确认的事实」，干扰项取自**别的真实任务**的
已验证事实。对照臂把别人的事实认成自己的——因为对话流里没有「任务边界」和「验证状态」
这两个字段，只有一片连续的文字。**这才是那 8 倍 token 差距背后真正买到的东西。**

`transcript` 臂 TNR 80% 看着不低，但它 TPR 是 0.0%——它只是在无差别说「否」，
不是在分辨。TNR 必须和 TPR 一起读，这也是判分器用均衡准确率而不是单看一列的原因。

### ② 「你们的对照组是稻草人」这个质疑，被数据本身否掉了

这是这一版最有价值的一条，因为它可能推翻我们自己：

> **mem0 没有跑赢我们自写的对照臂。** 它的事实召回 55.0% 低于我们自写词法 RAG 的 60.0%
> （区间大幅重叠，两者其实打平），四选一与 summary、transcript 并列 46.7%。

也就是说，0.3 那三个「自己写的」对照并不是被我们削弱的软柿子——一个被业界广泛引用的
真实 memory 系统，落在同一条带里。**这条比第①条更重要**：它把「对照组太弱」这个
最省事的反驳堵死了，而且是用一个我们无法操纵的第三方实现堵的。

### ③ 成本的不对称比分数更刺眼

mem0 为了得到那 55%，先花了 **44 次模型调用 / 55.2 万输入 token + 56.6 万输出 token / 68 分钟**
把 261,864 字符语料嚼成 382 条记忆。2origin 那一侧没有这道工序——学历是 AI 干活时顺手写的，
**「记住」不是一个额外的批处理阶段，而是干活的一部分**。

## 2.5 这一节记录一次「差点发出去的错误归因」

bench 从 spec 0.2 起就有一条地板线自查：**空上下文臂必须贴着瞎猜线**，否则说明题目泄题。
它查的是「题目对空手者是不是太容易」。**它的镜像一直没人查**：

> 题目对对照组是不是根本不可能？

真值取自磁盘上的 `task.origin.json`，而对照臂看到的是 `corpus.json` 里**钉死的**两份会话记录。
学历是活文件——后来的会话继续往里写事实，那些字句不可能出现在钉死的记录里。
不查这一条，「状态赢对话流」里就掺着一块「对照组没见过」，而两者含义完全不同：

- 前者是「同样的信息，结构化表示更好用」——这是我们想证的；
- 后者是「我们给对照组的语料里没有答案」——**这正是 v0.1 那个构造出来的结论，换了个地方复发**。

v0.1 的病是「对照组的 transcript 由脚本生成、从没写进 goal 原文」；
v0.4 差一点犯的是「对照组的 transcript 是真的，但答案有一半不在里面」。
形式换了，结构一模一样：**赢的不是方法，是对照组手里没牌。**

现在这条检查是 `bench/corpus-availability.mjs`，跑一次就打印可得性分布并按可得性拆分各臂。
它还有一条硬拦截：**学历指纹与跑结果时不一致就退出码 2**——拿现在的学历去解释当时的答案，
等于用新真值给旧答案打分。

**没有解决的部分**：那 10 条「不在语料里」的题，现在**既不能**算成 2origin 的胜利
（对照组没这条信息），**也不能**算成语料选择的偏差（我们只钉了 2 份会话，没钉全）。
它就是没被测量。要测，得把除「写 benchmark 的那个会话」以外的所有 task6 会话都钉进 corpus 再跑一遍。

## 3. 我们为了不打稻草人给 mem0 做的四件事（每件都可复现、可反驳）

| # | 做法 | 不做会怎样 |
|---|---|---|
| 1 | 同一份语料，字节级同一个文件（`cache/corpus-task6-261864.txt`，由 bench 写出后交给 python） | 各渲染一遍就不是同一个实验 |
| 2 | 还原成 role 标注的多轮消息再 `add()`，不是硬塞一坨纯文本 | mem0 是给对话设计的，喂纯文本等于人为削弱 |
| 3 | `custom_instructions` 要求保留源语言与原样标识符 | mem0 2.0.17 把 `use_input_language` **硬编码为 False**（`memory/main.py:938`），中文语料会被翻成英文存，题目是中文原句判别 → 平白多一层损耗。留了 `--default-prompt` 开关可复现默认行为 |
| 4 | `top_k=60`（实测 30 只填满 68% 预算，60 填到 9,366/9,405） | 对照组拿着 2/3 的预算去比，是另一种削弱 |

## 4. 这一轮在判分器和接线上抓到的四个缺陷

延续 `papers/self-attesting-evaluation.md` 的主题——**每一个都是「自报数字」与「磁盘真相」脱节**：

1. **推理模型烧掉 cap，整批语料静默消失。** mem0 抽取用 `max_tokens=4000` 时
   `finish_reason=length`，mem0 内部 JSON 解析失败后**静默返回 0 条记忆**——6,000 字符语料
   凭空从对照组的记忆里蒸发，而日志上只显示"这批 0 条"。
   这跟 spec 0.3 的 summary 臂翻的是**同一个车**，换了个部件复发。
   现在：cap 提到 24,000；一批返回 0 条就打印原始回复并重试一次；空批次与重试次数都进 stats。
2. **一页被当成了总数。** `mem0.get_all()` 的 `top_k` 默认 20，我拿它当"记忆库有多少条"，
   于是 **382 条被报成 20 条**，而 search 明明在 382 条上检索。
   现在：`store_count()` 显式要 `top_k=100000`，逼近上限时报警。
3. **预算记账漏了前缀。** 装载时按记忆正文长度计费，漏掉 `- ` 与换行，mem0 实测拿到
   9,733 字符（预算 9,723）。占便宜的对照也是坏对照。现在按最终字符串真实长度计。
4. **对照组被自己的默认参数饿着。** `top_k=30` 只装到预算的 68%，
   而 rag 臂是装到 98% 的。同预算的前提是**双方都真的用满预算**。

## 5. 诚实边界（没证明的部分）

- **「结构化状态更会找」没有证据。** 答案在语料里时 2origin 90% 与自写 RAG 90% 打平（n=10，
  区间完全重合）。本轮能讲的只有「更会拒绝」（TNR 100% vs 55–60%，区间不重叠）。
- **表格里 §1 的 97.5% vs 55% 不要单独引用。** 它掺着「对照组没见过」的那一半，
  必须与 §2/§2.5 的拆分一起读。
- **对照语料只钉了 2 份会话，没钉全。** 于是 10/20 条真事实的可得性缺口，
  既不能归因于表示形式，也不能归因于我们选语料——它没被测量。
- **两跳题依然分不开任何一臂，v3 的作废继续有效。** 2origin 71.9% 与空上下文臂 **71.9% 完全相同**，
  最高分是 summary 的 75.0%。「结构化状态让模型更会推理」这条**仍然没有任何证据支持**。
  可讲的只有事实召回。
- **单模型、单任务、单次运行，没有重采样。** v3 已实测同配置两次运行能差 13.3 个点，
  所以本表里 5 个点以内的差距一律不可读（例如 mem0 55.0% 与 rag 60.0% 之间没有可讲的差别）。
- **embedder 是本地 HuggingFace 模型，不是 mem0 默认的 OpenAI embedding。**
  原因是本机两个可用网关（`api.deepseek.com`、`api.u-claw.org.cn`）都没有 embeddings 接口
  （实测 404 / 503）。这是与 mem0 默认配置的一处真实偏离，可能影响其检索质量。
- **只接了一个第三方系统。** Letta / LangMem / Zep 都还没接，它们的记忆模型与 mem0 不同
  （尤其 Letta 的自编辑 memory block 在设计上离 2origin 更近）。
- **与 v3 的数字不可直接比较。** 学历是活文件，本轮 bundle 9,405 字符 / 76 题，
  v3 是 9,635 字符 / 79 题，语料本身变了。跨版本只能比结论，不能比小数点。
- **语料仍是我们自己的 9→10 份学历。** 外部效度问题没解决，只是把"对照实现"这一项解决了。

## 6. 复现

```bash
python -m venv .venv-mem0
./.venv-mem0/Scripts/python -m pip install mem0ai "mem0ai[extras]" sentence-transformers

# 只跑 mem0 臂（首次会 ingest，约 68 分钟，之后命中缓存）

# 全量七臂
node bench/shadowwork-bench-live.mjs --out bench/results-live-v4.json

# 对照语料可得性复核（§2/§2.5 那张拆分表就是它打的）

```

检查第三方臂在场、记忆库非空、无空批次、保留源语言（`2origin-computer/conformance/run-tests.sh`）。
